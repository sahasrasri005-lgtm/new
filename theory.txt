PART I – MAVEN
==================================================

1(c) Explain Maven lifecycle phases

1. clean:
   Removes files generated by previous builds, usually the target directory.

2. compile:
   Compiles the application's source code.

3. test:
   Runs the test cases of the project.

4. package:
   Packages the compiled application into the required format such as
   JAR or WAR.

5. install:
   Installs the generated package into the local Maven repository so that
   it can be used by other local Maven projects.

Phase that generates the WAR file:
   package

Easy order:
   clean → compile → test → package → install


1(e) Troubleshooting unsupported Java source/target version

The error may occur when the Java version configured in Maven does not
match the Java version required by the project.

Steps to troubleshoot:

1. Check installed Java:
   java -version

2. Check compiler:
   javac -version

3. Check Java used by Maven:
   mvn -version

4. Check JAVA_HOME and ensure it points to the required JDK.

5. Check pom.xml and verify that the source and target versions are
   configured as Java 17.

6. After correcting the Java configuration, run:
   mvn clean package

The purpose is to make sure the same required Java version is used by
the project and Maven.


1(f) WAR builds successfully but fails on Tomcat

Possible Cause 1: Java version mismatch
   The Java version used by Tomcat may be incompatible with the application.

Troubleshooting:
   Check java -version and verify the Java version used by Tomcat.

Possible Cause 2: WAR deployment problem
   The WAR file may not be present in Tomcat's webapps directory or may
   not have been deployed correctly.

Troubleshooting:
   Check the Tomcat webapps directory and verify that the WAR file is present.

Possible Cause 3: Tomcat/application configuration error
   The application may have an error during deployment.

Troubleshooting:
   Check the Tomcat logs for deployment or startup errors and verify that
   the application has been deployed correctly.


1(g) Project works on Java 17 but fails on Java 8

1. Identify the version mismatch:
   Run java -version and mvn -version on both machines and compare the
   Java versions.

2. Configure Maven to require Java 17:
   Set the Maven compiler source and target to 17 in pom.xml.

3. Why the same JDK version should be used:
   - Avoids version mismatch and compilation errors.
   - Provides consistent build results.
   - Ensures development and deployment environments are compatible.
   - Prevents an application built with one Java version from failing in
     another environment.

PART II – GIT & GITHUB
==================================================

2(e) Explain the complete merge conflict process

A merge conflict occurs when two branches modify the same part of a file
and Git cannot automatically decide which change to keep.

1. Identify the conflicted file:
   Use:
   git status

2. Open the conflicted file:
   Open course.jsp and find the conflict markers:

   <<<<<<< HEAD
   Your changes
   =======
   Other branch changes
   >>>>>>> branch

3. Resolve the conflict:
   Decide which code should remain, combine the required changes if
   necessary, and remove all conflict markers.

4. Stage the resolved file:
   git add course.jsp

5. Complete the merge:
   git commit

6. Push the result to GitHub:
   git push

Important:
   After resolving the conflict, do not run merge again.
   git commit completes the merge.


2(f) Explain staging, .gitignore and tracked files

If unwanted files are accidentally staged using git add ., they can be
removed from the staging area without deleting them from the computer.

1. Remove one file from staging:
   git restore --staged <file>

   OR:
   git rm --cached <file>

2. Remove all files from staging:
   git restore --staged .

3. Check which files are staged:
   git status

4. Create a .gitignore file:
   It contains files and folders that Git should ignore.

Example:
   .classpath
   .project
   .settings/
   target/
   *.log

5. Purpose of .gitignore:
   It prevents unwanted files such as Eclipse configuration files,
   build files and temporary files from being added to future commits.

Important:
   .gitignore mainly prevents untracked files from being added.
   Files that are already tracked must first be removed from tracking.


2(g) Two ways to handle an incorrect latest commit

CASE 1: Commit has NOT been pushed

Use:
   git reset --soft HEAD~1

This moves the branch back by one commit while keeping the changes.
The developer can correct the implementation and create a new commit.

Why use it:
   It is suitable when the commit is local and has not been shared.

CASE 2: Commit has ALREADY been pushed

Use:
   git revert HEAD

This creates a NEW commit that reverses the changes made by the incorrect
commit.

Why use it:
   It is safer for a shared repository because the existing commit history
   is not rewritten.

Easy difference:

   reset  → moves/removes the local commit
   revert → creates a new commit to undo the old commit

PART III – DOCKER
==================================================

3(a) Explain the Dockerfile

FROM maven:3.9-eclipse-temurin-17 AS build
   Uses a Maven image with Java 17 for building the application.

WORKDIR /app
   Sets /app as the working directory inside the container.

COPY . .
   Copies the project source code into the container.

RUN mvn clean package
   Builds the Maven project and generates the WAR file.

FROM tomcat:10
   Uses Apache Tomcat as the runtime environment for the web application.

COPY --from=build /app/target/ai-olms.war
/usr/local/tomcat/webapps/
   Copies the generated WAR from the build stage into Tomcat's webapps
   directory so Tomcat can deploy it.

EXPOSE 8080
   Declares that the application uses port 8080 inside the container.

Why multi-stage build:
   The first stage builds the application.
   The second stage contains only the runtime environment.
   This keeps the runtime image cleaner and avoids carrying Maven build
   tools into the final runtime stage.


3(c) Docker container is running but localhost:7012 cannot be accessed

Troubleshooting checks:

1. Check whether the container is running:
   docker ps

2. Check stopped containers:
   docker ps -a

3. Check application/container logs:
   docker logs <container_id>

4. Check container configuration:
   docker inspect <container_id>

Also verify port mapping:
   docker port <container_id>

The required mapping is:
   Host port 7012 → Container port 8080

So the application should be accessed using:
   http://localhost:7012


3(d) Container is running but browser shows 404 Not Found

Possible reasons:

1. WAR file was not copied correctly into Tomcat.
   Verify:
   docker exec -it <container_id> ls /usr/local/tomcat/webapps/

2. Tomcat failed to deploy the WAR.
   Check:
   docker logs <container_id>

3. Wrong application URL/context path.
   If the WAR is named ai-olms.war, the application may be available at:

   http://localhost:7012/ai-olms

   instead of only:

   http://localhost:7012

4. Deployment/application configuration error.
   Verify that Tomcat has extracted the WAR and created the application
   directory inside webapps.

Verification:
   docker exec -it <container_id> ls /usr/local/tomcat/webapps/

Expected:
   ai-olms.war
   and/or
   ai-olms/

VERY IMPORTANT THEORY TO MEMORIZE
==================================================

Maven:
   clean  = remove old build
   compile = compile source
   test = run tests
   package = create WAR/JAR
   install = put package in local repository

Git:
   restore = restore file
   merge = combine branches
   reset = move back local commit/history
   revert = new commit that undoes old commit
   push = send local commits to GitHub

Docker:
   WORKDIR = working folder inside container
   COPY = copy files into image
   RUN = execute command while building image
   EXPOSE = declare container port
   WAR = web application package
   Tomcat = runtime for the WAR application

KEY DIFFERENCES:

restore vs revert:
   restore → file
   revert → previous commit's changes by creating a new commit

merge vs push:
   merge → combine branches
   push → send commits to GitHub

reset vs revert:
   reset → suitable for unpushed local commit
   revert → suitable for already-pushed/shared commit

JAR vs WAR:
   JAR → normal Java application
   WAR → web application deployed to a servlet container such as Tomcat
